# FilePilot 目录规则与一键整理设计

更新日期：2026-07-26

进度状态：设计阶段，未开始实施。

## 目的

这份文档定义两件互相支撑的事：

1. **目标目录规则**：由 AI 与用户共同维护、可增量演进的「什么文件该进哪个目录」描述，挂在目标目录池上。
2. **一键整理**：对熟悉目录（下载目录等）应用已有规则，不再逐步操作，直接分类完成，事后给一份总结。

规则是资产，一键是它的消费方式。规则没形成好，一键不该开放；规则形成好了，一键就是自然结果。

## 与《定时扫描守门人设计》的关系

`incremental-gatekeeper-design.md` 作废，本文档取代它。取舍如下：

| 旧设计内容 | 处置 |
| --- | --- |

| 纠正学习 / 偏好沉淀 | **改造并入**，改动落在用户可见的规则文本上，不做隐式偏好记忆 |
| 定时轮询、常驻进程形态、单实例互斥 | **废弃**，一键整理是用户触发的，不需要常驻 |

## 非目标

- 不做后台定时扫描，不做常驻进程，不做文件系统监听。
- 不做独立的规则 DSL 或规则列表。规则依附在目录上，一个目录一条。
- 不做规则优先级/顺序/覆盖关系（依附在目录上天然不需要）。
- 不引入第三种 `organize_method`。

## 已定决策记录

以下决策已经过讨论确认，实施时不再重议：

| 决策点 | 结论 | 理由摘要 |
| --- | --- | --- |
| 信任对象 | 用户可读可改的规则文本，不是 AI 的判断 | 规则是静态资产，看一眼就知道对不对，改一次长期有效 |
| 规则载体 | 依附目标目录，一个目录一条描述 | 用户心智就是「这个文件夹放什么」；天然无规则冲突 |
| 一键的定位 | `assign_into_existing_categories` 的直通驾驶方式，不是新 method | 判定、约束、执行、journal 全部相同，只有是否停站不同 |
| 执行到哪一步 | 直接执行到完成，事后给总结 | 停在预览等于把流程步数换成审阅负担，一键的价值蒸发 |
| 拿不准的文件 | 增量模式留原地，大扫除进 Review 目录 | 两种模式的「原地」含义不同，见下文论证 |
| 规则生成 | 规则页上的一个动作，不是一种整理模式 | 它分析目标目录、不产生 move，塞进 organize_method 是概念错配 |
| 冷启动 | 首次使用引导 + 大扫除后自动反推规则初稿 | 一次性引导 ≠ 一种模式；从零手写规则是用户放弃的地方 |
| Review 机制 | 不废弃，三个身份并存 | 深度嵌入现有代码，且在大扫除下有新价值 |
| 空规则目录 | 一键前阻止并引导到规则页（可用 AI 初稿一键填） | 杜绝「什么都没配就一键」的失望；AI 初稿把门槛降到一次点击 |
| 同名冲突 | 跳过留原地，总结页给原因；不自动加后缀 | 永不产生歧义、不替用户改名；反复出现靠「已知跳过」机制收起 |
| 首页改版幅度 | 本轮最小侵入：加「分类规则」入口 + 一行常用整理卡片 | 不重排启动器两步流程，`LAUNCH_DEFAULT_*` 暂不收拢，完整改版留到下一轮 |

## 概念模型

三个概念，用户只需要认真关注第二个：

| 概念 | 含义 | 现状载体 |
| --- | --- | --- |
| 目标目录池 | 用户显式配置的一组目录，分类结果只能落在池内 | `TargetProfile.directories` |
| 规则 | 每个目录一句「什么样的文件该放进这里」 | `TargetProfileDirectory.description`（`app/models.py:193`） |
| 一键整理 | 对某个源目录应用某套规则，直接分类完成 | 待建，复用现有 stage 机 |

### 信任论证

一键整理敢开放，依赖三条：

1. **不删除文件**：任何路径下都不产生删除。
2. **目标限定在池内**：AI 只能输出池内 slot_id，无法发明目标。
3. **可读的规则**：用户信任的是自己校订过的规则文本，不是不可检验的模型判断。

三条同时成立时，最坏情况是「分得不够准」，而不是「丢文件」。

## 安全边界的三个口子

上述论证在当前代码上有三处不成立，是一键的硬前置：

### 1. 目录池约束当前是软的

`app/target_slot_registry.py` 的 `ensure_slot()` 遇到池外路径会**自动追加新 slot**。这在大扫除下是特性（AI 需要能提议新建目录），在一键归档下是漏洞。

**改动**：`ensure_slot` 增加严格模式，`assign_into_existing_categories` 走严格模式——池外目标直接拒收，不扩池。

### 2. 同名冲突会让整批失败

`execution/service.py:220` 把「目标已存在」记为 blocking error，`can_execute = not blocking_errors`。用户下载了两次同名文件，整次一键全废。

`rollback/service.py:127` 同理，回退是全盘阻断——一个文件被占用，整批撤不了。

**改动**：两处都改成 per-item `skippable + reason`，报告如实呈现「已处理 N 项 / 跳过 M 项及原因」。**不允许用覆盖解决冲突**，那会破坏「不删除文件」这条保证。

### 3. 移错位置 = 找不到 = 体感等于丢了

所以总结与查找不是收尾的礼貌动作，它是安全论证的组成部分。见「记录与查找」。

## 可移动性前置检查

在生成计划之前先过的本地事实检查，模型无法也不应判断这些。从旧设计并入，适用于所有 organize_method：

| 信号 | 规则 | 实现 |
| --- | --- | --- |
| 下载中 | `.part` / `.crdownload` / `.!qB` 等后缀 | 后缀匹配 |
| 占用 | 独占方式打开失败 → 跳过 | Windows 独占 open 尝试 |
| 成套文件 | 同名异扩展（`X.mkv`+`X.srt`）、`X.html`+`X_files/`、含 `.dll` 同级的 `.exe` → 整组不动 | 文件名模式匹配 |
| 云占位文件 | OneDrive 按需文件占位符不动 | `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` 属性检测 |
| 云同步目录 | 同步目录整体排除（移动=删+重传，会触发同步风暴） | 目录级判定，非逐文件 |
| 目录级安全 | 源目录须通过 `app/safety.py` 的 `unsafe_source_path_reason` | 复用现有 |

输出 `movable: bool + skip_reason`，未通过者记入总结，原因用户可见。

## 规则

### 载体

复用 `TargetProfileDirectory` 的 `description` 字段，不新增概念。当前它是「目录说明（可选）」，需要升格为主字段。

一个目录一条描述，天然不存在「两条规则抢同一个文件」的问题——这绕开了规则优先级、顺序、覆盖关系的整个复杂度分支。

### 可选的硬条件

允许在自然语言描述之外挂几条确定性条件（扩展名白名单、文件名 glob）。命中硬条件的文件不调模型，直接分类。

价值：完全可预期、总结里可解释、顺带省调用。

**它是可选的加速层，不是必需层。** 不能让用户为了使用软件先学会写规则。

### 形成路径（三个时机）

**1. 冷启动：从目录现有内容反推**

AI 读每个目标目录的现有文件，生成描述初稿并附依据（「目录现有 32 个 PDF 和 8 个 docx，多为技术手册与 API 文档」）。用户的目录里已经沉淀了他的分类意图，不需要从零写。

从零写规则是绝大多数人会放弃的地方，必须绕过它。

**2. 每次整理后的缺口回填（主引擎）**

这次没把握的文件就是规则缺口的精确定位。总结页直接问「这 5 个文件我没把握，要不要为它们补条规则？」用户点一下，规则长出一点。

规则的完备性靠使用驱动，所以入口是**任务式的「打磨规则」**，不是设置页里的一张表单。

**3. 纠正回流**

用户认为某条分类错了 → 点「放错了」→ AI 提议修改哪条目录描述。

**关键：改动必须落在用户能看见的规则文本上，不能变成隐式的偏好记录。** 用户看得见规则在变，「共同维护」才是真的；否则又回到了信任不可检验的 AI 记忆。

### 规则怎么写才管用

**重点在边界，不在中心。** 真正需要规则的从来不是「PDF 放文档」，而是「发票类 PDF 放财务、不放文档」。

因此 AI 应主动寻找**语义重叠的目录对**（两个目录描述互相沾边），向用户提一个具体的二选一问题。一个好的二选一比让用户写五条规则更有效、更省力。

### 规则快照

每次整理的 journal 里存下**当时的规则内容**（不是只存 `profile_id`）。规则会演进，半年后回看旧总结必须还能理解当时为什么那么分。

## unresolved 的三种落地

### 现状：信号与动作已经解耦

现有机制不是「AI 把文件分给 Review 目录」。`organize/prompts.py:24` 要求模型把拿不准的项登记进 `unresolved_adds`，**由系统映射到待确认区**（映射发生在 `app/session_service.py:566/598`、`app/execution_app_service.py:164/177`）。

所以问题不是「要不要废弃 Review」，而是「unresolved 这个信号该落地成什么」——而落地方式可以按模式不同。

### 为什么两种模式不对称

| | 频率 | 值守 | 源目录归宿 | unresolved 落地 |
| --- | --- | --- | --- | --- |
| 大扫除 `categorize_into_new_structure` | 一次性 | 有人 | 要被清空重构 | 物理 Review 目录 |
| 一键归档 `assign_into_existing_categories` | 反复 | 无人 | 本来就在，继续用 | 留原地 + 总结列表 |

**归档模式**：源目录（下载）整理后继续存在、继续被使用。留原地 = 它本来就在那儿，下次整理再看一遍。零成本。而反复累积的 Review 会变成第二个下载目录。

**大扫除**：目标是把混乱目录重构成整洁骨架。若 30 个无家可归的文件散在根目录、夹在新建的整齐目录之间，恰恰是大扫除要消灭的状态——留原地在这里是破坏产出物。且大扫除一次性、有人值守，Review 当场就会被处理。

### Review 的三个身份

1. **大扫除的物理目录**：保留，并升级为**规则缺口收集器**——Review 里的文件正是规则覆盖不到的东西，用户处理它的过程就是规则第一次变完备的过程。
2. **增量模式的系统机制**：退场。unresolved 不再映射成 move。
3. **用户可选的普通目录**：想要「归档后源目录清空」体感的用户，自己在池里加一个「待分类」目录并写上规则（「实在拿不准的放这里」）。它是普通池成员，用户显式命名、可随时删除，与「一切都在用户给的目录池内」完全一致。

### 具体改动

- `unresolved_adds` 信号层**完全不动**（模型侧、id registry、快照沿用）。
- 增量模式下 unresolved 不产生 move，直接进总结列表——改 `session_service.py` 与 `execution_app_service.py` 那几处映射，按 organize_method 分支。
- 增量模式的 slot 池不再注入 Review slot（模型想选也选不到，正好印证池白名单的价值）。
- prompt 改两句：`organize/strategy_templates.py:339`、`organize/prompts.py:34` 里「交给系统放入待确认区」改为「登记为待补规则项，系统不会移动它」。
- 前端 review 分支代码**全部保留**（`completion-view.tsx`、`app/history_app_service.py` 的 `is_review` 判断），增量模式下自然走不到。删掉会弄坏大扫除。
- 文案：`frontend/src/app/settings/launch-tab.tsx:187` 「拿不准的项目进入待确认区」需改写。

## 一键整理对现有流程的改动

### stage 机不变，只是不停站

现有链条全部保留：

```
draft → scanning → [selecting_incremental_scope] → planning
      → ready_for_precheck → ready_to_execute → executing → completed
```

新增的不是 stage，而是 session 上一个 `unattended` 标记，让 orchestrator 在两个 `ready_*` 处自动推进而非等待前端调用。恢复、中断、历史、回退全部沿用现有机制。

### 逐项改动

| 位置 | 改动 |
| --- | --- |
| `app/session_constants.py` | 不加新 stage；session 模型加 `unattended` 标记 |
| `app/session_orchestrator.py` | `unattended` 时自动推进 precheck → execute |
| `incremental-selection-view.tsx` 对应 stage | 一键下跳过，默认全量 |
| `app/planning_conversation_service.py` | planning 降为单次结构化调用；**保留「转成会话」出口**，用户看完总结不满意时可转为可对话会话接着调 |
| `execution/service.py:220` | 同名冲突从 blocking 改为 per-item skip |
| `rollback/service.py:127` | 全盘阻断改为 per-action `skippable + reason` |
| `execution/service.py:26` | 去掉 `JOURNAL_CHECKPOINT_INTERVAL`，改 write-ahead：每条 move 执行前落意图、执行后标结果 |
| `app/target_slot_registry.py` | `ensure_slot` 严格模式 |
| `organize/prompts.py` | 注入规则文本；改 unresolved 措辞 |
| journal schema | 增加规则快照、依据字段（命中规则 / AI 判断）、文件身份字段（size + mtime） |

### 为什么不做成第三种 organize_method

`organize/strategy_templates.py` 已有 `task_type / organize_mode / organize_method` 三向映射及一致性校验。增加第三种 method 会让这套映射再膨胀一圈，而一键与归档模式的判定、约束、执行、journal 完全相同，唯一区别是是否停站——那是驾驶方式，不是 method。

## 界面信息架构

### 规则必须从设置页深处提出来

当前规则位于「设置 → 目标目录 → 展开某个目录 → 目录说明（可选）」，四层深且标着「可选」。它是新方案里最核心的用户资产，落位完全错配。

| 调整 | 说明 |
| --- | --- |
| 新增一等入口 | 侧栏/首页「分类规则」；`settings/target-profiles-section.tsx` 变成同一组件的第二入口 |
| description 升为主字段 | placeholder 从「目录说明（可选）」改为「什么样的文件应该放进这里？」，旁边展示 AI 初稿及其依据 |
| 展示形态改版 | 从路径列表改为规则卡片：目录名 + 一句话规则 + 最近命中数。用户看的是规则，不是路径 |

### 启动器

当前是 `launcher/source-step.tsx → launcher/strategy-step.tsx` 两步。

一键需要的是**一张可直接点的卡片**：「整理〈下载〉· 按〈我的规则〉」。首页上方开「常用整理」区，每张卡是一个 (源目录 + profile) 组合。现有 `LAUNCH_DEFAULT_*` 那批设置本质上就是在攒这个，顺势收拢。

### 进度页

`/workspace/progress` 当前分阶段展示。一键下退化为单一进度（「正在分类 42 个文件」）——用户不关心 scanning 与 planning 的区别。

### 结果页

复用 `/workspace/result` + `completion-view.tsx` + `directory-tree-diff.tsx`，但内容重心从「执行报告」转向「**本次分类总结**」：

- 首屏一句话 + 三个数字：「整理〈下载〉：42 个归位，8 个未处理，0 个失败」。展开才是目录树。
- **「未处理」与「已归位」同等醒目，每条带原因。** 这是最容易被做成折叠小字的地方，而它恰恰是用户判断这次靠不靠谱的依据；看不到跳过项，用户的默认假设是「漏了」。
- 按目标目录分组，不按 move 平铺。用户的心智是「我的下载目录现在变成什么样了」。
- 每条标明依据：命中哪条规则 / AI 判断。
- **必须带「打磨规则」动作**：没把握的那几个 → 补规则。这是规则增量的主引擎，入口只能在这里，因为这是用户唯一会带着具体问题看规则的时刻。
- 报告是可长期停留、可重新打开的页面，不是执行完的弹窗。数据源必须是 journal（`get_journal_summary` 已经是了），不依赖内存 session。

### 顺带修一处不一致

`app/history_app_service.py` 的 `list_history` 把 session 与 execution 混在一个列表里，两者 `item_count` 语义不同（前者是计划的 `move_count`，后者是 journal 实际条目数）。总结入口挂上去之前先统一。

## 冷启动与首次引导

### 规则生成是规则页上的一个动作

它分析**目标目录池**（读每个目录现有内容 → 反推它实际在放什么），**不涉及源目录，不产生任何 move**。它不是一次「整理」。

- 不污染 session/stage 机——不新增 stage、不进历史、不写 journal、不需要回退。
- **可随时重跑，只为新增目录生成**——这就是「增量」；做成一次性向导就做不到。
- 直接复用 `app/async_scanner.py` 与 `analysis/`，只是分析对象从源目录换成目标目录。

### 两条进入路径

1. **首次使用引导**：检测到用户还没有任何 profile 时，首页给出「先建立你的目录规则」。一次性引导 ≠ 一种模式。
2. **大扫除后自动反推**（推荐路径）：大扫除完成后追加一次调用，把产出的目录结构反推成规则初稿。

第二条把两种 method 串成完整叙事——**大扫除是安装向导，规则是它的产出物，一键是此后的日常**——比让用户面对空白的规则页强得多。

## 记录与查找

### 记录

- journal write-ahead（见改动表）。一键执行频率上升、用户注意力下降，崩在两次 checkpoint 之间就是「文件动了但没记录」，这是唯一不可恢复的坏情况。
- 每条记录存：规则快照、判定依据（命中规则 / AI 判断）、文件身份字段（size + mtime）。
- 保留期与体积轮转策略：一键会让执行次数上升一个量级，`EXECUTION_LOG_DIR` 需要上限。

### 查找

**一键整理最大的风险不是「移错了」，是「我的文件找不到了」。**

核心能力：输入文件名片段 → 它现在在哪、哪次整理动的、一键在资源管理器定位。

当前历史是**执行粒度**的（`list_history` 一次执行一行），需要新增**文件粒度**检索：

- 短期直接 glob `EXECUTION_LOG_DIR/*.json` 匹配（几十次执行内无感）。
- 上到几百次执行后建轻量倒排索引（文件名 → execution_id + item_id）或 SQLite。**可以延后，但 journal 的 item 字段要一开始就留够。**
- 结果要能跳回那次整理的完整总结页。

这个入口的优先级**高于**结果页的任何美化。

## 并发

一键会被连点、或两个窗口对同一目录同时触发。需要**源目录粒度的互斥**（谁持有谁执行，另一方明确报错而非静默排队）。比常驻进程的单实例要求轻得多，但不能没有。

## 反复一键的疲劳问题

同一个下载目录每周一键，上次跳过的项这次会再次出现。需要记住「已知跳过项」，总结页默认收起，只突出本次新增的。否则每份总结都在重复同样的 20 条，用户会停止阅读——而停止阅读总结，等于失去了唯一的纠错通道。

## 实施阶段

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| P0 | journal 硬化（write-ahead + 规则快照 + 依据 + 身份字段）、逐项回退、同名冲突改 per-item skip | 无 |
| P1 | 文件级查找入口（先 glob 实现） | P0 |
| P2 | 规则载体升格（description 主字段 + 硬条件）、规则页一等入口、AI 生成规则初稿 | 无（可与 P0 并行） |
| P3 | 一键管线（`unattended` 标记 + 自动推进 + 严格 slot 模式 + 可移动性前置检查）、unresolved 按模式分流 | P0 + P2 |
| P4 | 总结页改版（分组 + 未处理同等可见 + 依据 + 打磨规则入口）、启动器常用整理卡片 | P3 |
| P5 | 大扫除后自动反推规则、首次使用引导 | P2 |

P0 与 P2 可并行；P3 必须等两者都完成。

## 成立标准

- 用户在一键之后不需要打开源目录核对，只看总结即可确认。
- 规则页上每个目录都有非空且用户校订过的描述。
- 「未处理」项数量随使用次数下降（规则在变完备）。

## 主要风险

| 风险 | 缓解 |
| --- | --- |
| 用户不写规则就直接一键 | 规则为空的目录在一键前明确阻止并引导到规则页；AI 初稿降低填写门槛 |
| AI 生成的规则初稿过于笼统，用户照单全收 | 初稿必须附依据（基于目录现有内容），并主动就重叠目录对提二选一问题 |
| 总结页被用户忽略 | 首屏三个数字 + 未处理项同等醒目 + 已知跳过项收起，控制每次阅读量 |
| 云同步目录里执行移动引发同步风暴 | 同步目录默认整体排除，目录级判定而非逐文件 |
| 规则演进后旧总结无法理解 | 规则快照随 journal 存储 |
